## Achados

[RISCO] internal/db/sqlite/account_tokens.go:76-80 + internal/adminui/admin.go:214 — O `POST /admin/redeem` é público, não passa pelo limitador de login (`h.login`/`httprate`) e executa um bcrypt `DefaultCost` antes de consultar o token, para qualquer tentativa com CSRF de pré-autenticação (que se obtém livremente) e senha de formato válido. Isso permite amplificar CPU sem autenticação. A força bruta do token continua inviável (256 bits). O bcrypt antecipado também não protege contra oráculo de tempo: em caso de acerto, o sucesso já é visível na resposta, e todos os casos de falha (conta inexistente, token errado, expirado, consumido ou de outra finalidade) seguem o mesmo caminho barato de digest. Correção sugerida, a decidir com o usuário (o doc-041 §9 proíbe limitador novo, mas não reaproveitar o existente): (a) comparar o digest numa leitura, rodar o bcrypt só se houver acerto e consumir na transação de escrita com `DELETE FROM account_tokens WHERE user_id=? AND token_hash=? AND expires_at>unixepoch()` verificando `RowsAffected==1` antes de `setAccountPassword`; e/ou (b) envolver o POST de resgate no mesmo middleware compartilhado do login.

[RISCO] internal/db/sqlite/account_access.go:27-70 — Alterar o papel não invalida um token pendente da conta. Exemplo: o root emite um token de recuperação para um usuário comum e, dentro dos 30 minutos, promove esse usuário a admin. O token ainda válido passa a definir a senha de uma conta admin. A emissão foi legítima e a janela é curta, então o risco é baixo. Correção sugerida: `DELETE FROM account_tokens WHERE user_id=?` na mesma transação de `updateAccountAccess` sempre que o papel mudar, ou registrar como comportamento aceito.
